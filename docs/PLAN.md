# Покроковий план розробки (навчальний)

Цей план — для Володі: як крок за кроком побудувати застосунок кооперативу разом з AI-асистентом (ChatGPT, Claude тощо).
Опис самого проєкту та вимоги — у [PROJECT.md](PROJECT.md). Налаштування безпечного середовища — у [SETUP.md](SETUP.md). Правила для AI-асистента — у [AGENTS.md](../AGENTS.md).

## Як працювати з планом

Кожен крок має однакову структуру:

- **Мета** — що отримаємо в кінці кроку.
- **Що вивчити** — нові поняття, які з'являються на цьому кроці.
- **Що зробити** — дії по порядку.
- **Промпт для AI** — готовий текст, який можна вставити в чат з асистентом (на початку кожної розмови додавай посилання на `docs/PROJECT.md` і `docs/PLAN.md`).
- **Перевірка** — як переконатися, що крок виконано. Не переходь далі, поки перевірка не пройдена.

**Правила роботи**

1. Один крок — одна гілка в Git і один pull request (PR). Не пушити напряму в `main`: з `main` сайт одразу публікується для бухгалтера.
2. Перед тим як приймати код від AI — попроси пояснити кожен файл своїми словами. Якщо не розумієш — питай, доки не зрозумієш.
3. Після кожного кроку — показати результат на телефоні (і бухгалтеру, коли з'являється інтерфейс).
4. Персональні дані членів кооперативу (ПІБ, телефони, скани) **ніколи не комітити в Git** — тільки в базу даних.

## Етап A. Підготовка (1–2 дні)

### Крок A1. Інструменти та доступи

- **Мета:** у Володі все встановлено і є доступ до проєкту.
- **Що вивчити:** що таке Git, GitHub, термінал, Node.js.
- **Що зробити:**
  1. Прийняти запрошення в репозиторій `vm-cpu/cooperative` і в акаунт Cloudflare.
  2. Встановити: Git, Node.js (LTS), VS Code, GitHub CLI.
  3. Клонувати репозиторій, виконати `npm install`, потім `npm run dev`.
- **Промпт для AI:**
  > Я початківець. Допоможи встановити Git, Node.js, VS Code і GitHub CLI на мій комп'ютер (у мене <Windows/Mac>). Потім поясни, як клонувати репозиторій vm-cpu/cooperative і запустити його локально командою npm run dev. Веди мене по одному кроку і чекай мого підтвердження.
- **Перевірка:** на `http://localhost:8787` відкривається сторінка «Кооператив», а `/api/health` повертає `{"ok":true,...}`.

### Крок A2. Перший pull request

- **Мета:** пройти весь цикл «гілка → зміна → PR → злиття → сайт оновився».
- **Що вивчити:** гілка, коміт, push, pull request, автодеплой Cloudflare.
- **Що зробити:** у новій гілці змінити текст на `public/index.html`, створити PR, злити його в `main`, дочекатися деплою.
- **Промпт для AI:**
  > Поясни простими словами, що таке гілка, коміт і pull request у Git. Потім проведи мене через: створити гілку, змінити текст у public/index.html, закомітити, запушити і відкрити pull request на GitHub.
- **Перевірка:** зміна видна на робочому сайті Cloudflare (адреса `*.workers.dev`).

### Крок A3. Автоматичні перевірки (CI) з першого дня

> ✅ Вже налаштовано (PR «Secure dev environment»). Завдання для Володі — **розібратися**, як це працює: прочитати `.github/workflows/ci.yml`, `eslint.config.js`, `vitest.config.js`, `test/index.test.js` і пояснити своїми словами; додати свій тест. Ручні кроки (branch protection, 2FA) — у [SETUP.md](SETUP.md).

- **Мета:** кожен PR автоматично перевіряється, поганий код не потрапляє в `main`.
- **Що вивчити:** CI (GitHub Actions), лінтер, форматер, тести, branch protection.
- **Що зробити:**
  1. Додати ESLint + Prettier, скрипти `npm run lint`, `npm run format:check`.
  2. Додати тести: Vitest (+ `@cloudflare/vitest-pool-workers` для коду Worker'а), скрипт `npm test`.
  3. GitHub Actions workflow `.github/workflows/ci.yml`: на кожен PR — install → lint → format check → test → `wrangler deploy --dry-run` (перевірка збірки).
  4. У налаштуваннях GitHub увімкнути **branch protection** для `main`: злиття тільки через PR і тільки якщо CI зелений.
  5. Увімкнути **Dependabot** (оновлення залежностей і сповіщення про вразливості).
- **Промпт для AI:**
  > Налаштуй у моєму проєкті Cloudflare Workers: ESLint, Prettier, Vitest з @cloudflare/vitest-pool-workers і один тест для /api/health. Потім створи GitHub Actions workflow, який на кожен pull request запускає lint, перевірку форматування, тести і wrangler deploy --dry-run. Поясни, як увімкнути branch protection для main.
- **Перевірка:** навмисно зламаний тест у PR робить CI червоним, і кнопка злиття недоступна.

## Якість: перевірки, тестування, аудити

Це правила, які діють на **кожному** кроці, починаючи з A3.

### Чекліст для кожного PR

- [ ] CI зелений (lint, формат, тести, збірка).
- [ ] Для нової логіки є тести (див. «Тестування»).
- [ ] Код переглянуто (див. «Code review»).
- [ ] Перевірено на телефоні (Android і, якщо є, iPhone) у прев'ю Cloudflare.
- [ ] Нема секретів і персональних даних у коді та комітах.
- [ ] Оновлено документацію, якщо змінилась поведінка.

### Тестування

| Вид                        | Що перевіряє                                                                               | Інструмент                                                                  | Коли                     |
| -------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- | ------------------------ |
| **Unit-тести**             | Окремі функції: розрахунок боргу, пошук, парсинг номера `ряд-бокс`                         | Vitest                                                                      | З кроку A3, на кожен PR  |
| **Інтеграційні тести API** | Ендпоінти Worker'а з тестовою D1: доступ без входу заборонено, голова не може редагувати   | Vitest + `@cloudflare/vitest-pool-workers`                                  | З кроку B3 / C3          |
| **E2E-тести**              | Сценарії бухгалтера в браузері на розмірі телефона: увійти → знайти гараж → додати телефон | Playwright (мобільний viewport)                                             | З кроку C4, у CI         |
| **Тести доступності**      | Контраст, підписи до кнопок і полів, розмір зон натискання                                 | axe-core (`@axe-core/playwright`), Lighthouse CI (поріг Accessibility ≥ 95) | З кроку C2, у CI         |
| **Ручне тестування**       | Реальний телефон бухгалтера, реальні завдання                                              | Чекліст з кроку C7                                                          | Наприкінці кожного етапу |

Правило: **знайшли баг — спочатку пишемо тест, який його відтворює, потім виправляємо.**

### Code review

- Кожен PR переглядає **інша людина** (або, поки Володя сам, — AI-рев'ю + перегляд того, хто його навчає).
- AI-рев'ю: перед злиттям попросити асистента:
  > Зроби code review цього pull request: знайди баги, проблеми безпеки (доступ без авторизації, SQL-ін'єкції, витік персональних даних), проблеми доступності і місця, які можна спростити. Для кожної знахідки поясни, чому це проблема.
- Володя відповідає на кожен коментар: виправив або пояснив, чому ні.

### Аудити (регулярно)

| Аудит                | Що робимо                                                                                                                                | Як часто                                              |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **Безпека**          | Перевірити: усі `/api/*` вимагають входу; ролі працюють; SQL лише через параметри; файли R2 не доступні публічно; сесії мають термін дії | Наприкінці кожного етапу                              |
| **Залежності**       | `npm audit`, Dependabot-сповіщення, оновлення пакетів                                                                                    | Щотижня (Dependabot) + перед кожним етапом            |
| **Персональні дані** | У Git немає ПІБ, телефонів, сканів; доступ до бази мають тільки потрібні люди; є резервні копії                                          | Щомісяця                                              |
| **Доступність**      | Lighthouse + тест з бухгалтером на її телефоні                                                                                           | Наприкінці кожного етапу                              |
| **Продуктивність**   | Lighthouse Performance на мобільному профілі, швидкість відкриття на поганому інтернеті                                                  | Наприкінці кожного етапу                              |
| **Резервні копії**   | Експорт D1 (`wrangler d1 export`), перевірка, що з копії можна відновитись                                                               | Щотижня автоматично, перевірка відновлення — щомісяця |

### Моніторинг Cloudflare

- **Що дивитися:** Cloudflare Dashboard → Workers & Pages → `cooperative` → **Metrics** (запити, помилки, час CPU) і **Logs** (у `wrangler.jsonc` вже увімкнено `observability`).
- **Ліміти безкоштовного плану** (на момент написання; перевірити актуальні на сайті Cloudflare):
  - Workers: 100 000 запитів на добу;
  - D1: 5 ГБ даних, 5 млн прочитаних рядків і 100 000 записаних рядків на добу;
  - R2: 10 ГБ файлів, 1 млн операцій запису і 10 млн операцій читання на місяць.
    Для кооперативу з двома користувачами це з великим запасом; найшвидше росте **R2** (скани) — стискати фото перед завантаженням.
- **Сповіщення:** Cloudflare → **Notifications**: налаштувати email-сповіщення про помилки Worker'а і про наближення до лімітів / рахунку (Billing / Usage).
- **Щотижнева перевірка (5 хвилин):** кількість помилок за тиждень, використання D1 і R2, чи пройшла резервна копія. Записувати в `docs/MONITORING.md`.
- **Ендпоінт `/api/health`:** розширити перевіркою з'єднання з D1 і R2; підключити безкоштовний зовнішній моніторинг доступності (наприклад, UptimeRobot), щоб отримувати сповіщення, якщо сайт недоступний.

## Етап B. Дані (2–3 дні)

### Крок B1. Розібратися з даними кооперативу

- **Мета:** розуміти, які дані є і в якому вони стані.
- **Що є зараз:** документ «Список членів кооперативу ГБК “Ювілейний” 2026 р.» (Word, таблиці). Що з нього видно:
  - **574 бокси** у **9 рядах**: 1 (48), 2 (120), 3 (93), 5 (83), 6 (62), 7 (32), 8 (7), 9 (87), 10 (42). **Ряду 4 немає** — уточнити чому.
  - Номер гаража має формат `ряд-бокс`, наприклад `2-54`.
  - **12 боксів без власника:** 2-20, 2-32, 2-85, 2-106, 3-7, 3-40, 3-77, 5-21, 5-66, 7-12, 9-65, 10-3.
  - **3 технічні бокси:** 3-46, 9-70, 10-41.
  - **526 різних власників**; у 13 людей кілька боксів (одна людина — 14 боксів, ще одна — 8; уточнити, хто це).
  - Деякі частини списку повторюються в документі двічі, з невеликими розбіжностями в написанні (наприклад «Домбровський Я.» / «Домбровський Я.Ю.»).
  - Є лише прізвище та ініціали, **немає телефонів, email, документів** — їх треба буде додавати.
- **Що зробити:** перетворити Word-документ у таблицю (CSV) `ряд, бокс, гараж, власник`, виправити розбіжності, позначити порожні й технічні бокси.
- **Промпт для AI:**
  > У мене Word-документ зі списком гаражів у таблицях (колонки: «Ряд-бокс», «ПІБ»). Частина таблиць повторюється. Напиши скрипт на Python, який збере всі рядки в CSV (row, box, garage, owner), прибере дублі і виведе список розбіжностей, порожніх і технічних боксів.
- **Перевірка:** CSV має 574 рядки; розбіжності та питання записані й передані бухгалтеру. **CSV не комітити в Git.**

### Крок B2. Спроєктувати базу даних

- **Мета:** схема бази, в яку ляжуть усі дані.
- **Що вивчити:** таблиця, рядок, первинний ключ, зв'язок «один-до-багатьох», SQL.
- **Що зробити:** описати таблиці:
  - `garages` — ряд, бокс, номер, тип (звичайний / технічний), примітки;
  - `members` — ПІБ, телефон, email, месенджер;
  - `ownerships` — хто якого гаража власник і з якої дати (так зберігається історія переоформлень);
  - `documents` — скани, прив'язані до гаража або члена;
  - `payments`, `charges`, `meter_readings` — на етап платежів (поки тільки на папері).
- **Промпт для AI:**
  > Ось опис проєкту (docs/PROJECT.md). Запропонуй схему бази даних SQLite для Cloudflare D1: гаражі, члени кооперативу, власність з історією, документи. Поясни кожну таблицю і зв'язки простими словами, потім дай SQL-міграцію.
- **Перевірка:** Володя може пояснити, чому власник зберігається в окремій таблиці `ownerships`, а не прямо в `garages`.

### Крок B3. Створити базу в Cloudflare і завантажити дані

- **Мета:** реальні дані в D1.
- **Що вивчити:** Cloudflare D1, `wrangler`, міграції.
- **Що зробити:** `wrangler d1 create cooperative-db`, додати базу в `wrangler.jsonc`, застосувати міграцію, імпортувати CSV з кроку B1.
- **Промпт для AI:**
  > Допоможи створити базу Cloudflare D1 для мого Worker'а (wrangler.jsonc додаю), застосувати SQL-міграцію локально і на сервері, і написати скрипт імпорту CSV у таблиці garages, members і ownerships.
- **Перевірка:** запит `SELECT COUNT(*) FROM garages` повертає 574.

## Етап C. Перша версія застосунку (1–2 тижні)

### Крок C1. Основа PWA

- **Мета:** застосунок встановлюється на телефон.
- **Що вивчити:** PWA, manifest, service worker, mobile-first.
- **Що зробити:** додати `manifest.webmanifest`, іконки, service worker з кешем; обрати фреймворк для інтерфейсу (порадитися з AI, з поясненням чому).
- **Промпт для AI:**
  > Перетвори мій проєкт на Cloudflare Workers на PWA: manifest, іконки, service worker з офлайн-кешем. Інтерфейс — для телефона. Поясни кожен файл.
- **Перевірка:** на телефоні з'являється «Додати на головний екран», застосунок відкривається без адресного рядка.

### Крок C2. Дизайн для бухгалтера (доступність)

- **Мета:** базові стилі й компоненти, зручні для літньої людини.
- **Що вивчити:** доступність (accessibility), WCAG, контраст, розмір зон натискання.
- **Що зробити:** шрифт від 18–20 px, кнопка «А+», контраст AA/AAA, кнопки від 48×48 px з текстом, світла тема. Див. розділ «Доступність» у PROJECT.md.
- **Промпт для AI:**
  > Головний користувач — літня жінка-бухгалтер на телефоні. Зроби базові стилі та компоненти (кнопка, поле, картка, пошук) за вимогами з розділу «Доступність» у docs/PROJECT.md. Перевір контраст за WCAG AA.
- **Перевірка:** бухгалтер без підказок читає текст і натискає кнопки на своєму телефоні.

### Крок C3. Вхід у застосунок

- **Мета:** доступ тільки для бухгалтера й голови.
- **Що вивчити:** автентифікація, сесії, ролі.
- **Що зробити:** вхід за кодом з email (без пароля), дві ролі — бухгалтер (редагує) і голова (тільки перегляд); сесія на телефоні живе довго.
- **Промпт для AI:**
  > Додай у мій Cloudflare Worker вхід за одноразовим кодом на email і дві ролі: "accountant" (читання і запис) і "chair" (тільки читання). Сесія — довга, щоб літній людині не доводилось входити щоразу. Поясни, як це захищено.
- **Перевірка:** без входу дані недоступні (і через `/api/...` теж); голова не може нічого змінити.

### Крок C4. Список гаражів і пошук

- **Мета:** знайти гараж за номером або прізвищем за кілька секунд.
- **Що зробити:** головний екран — великий пошук; нижче список рядів (1, 2, 3, 5, …), у ряду — бокси з прізвищами; позначки «без власника» і «технічний».
- **Перевірка:** пошук «2-54» і пошук за прізвищем знаходять гараж; працює на телефоні однією рукою.

### Крок C5. Картка гаража

- **Мета:** уся інформація про гараж на одному екрані.
- **Що зробити:** номер, власник, телефон (натиснув — подзвонив), email, документи; бухгалтер може редагувати, з автозбереженням.
- **Перевірка:** бухгалтер сама додає телефон власнику.

### Крок C6. Документи та фото

- **Мета:** скани й фото документів у картці гаража.
- **Що вивчити:** Cloudflare R2 (сховище файлів).
- **Що зробити:** кнопка «Сфотографувати документ» (камера телефона), завантаження в R2, перегляд у картці.
- **Перевірка:** фото, зроблене на телефоні бухгалтера, видно голові у його застосунку.

### Крок C7. Тест з бухгалтером

- **Мета:** переконатися, що перша версія справді зручна.
- **Що зробити:** дати бухгалтеру 5 завдань (знайти гараж, додати телефон, сфотографувати документ…), мовчки спостерігати, записати, де вона затрималась. Виправити.
- **Перевірка:** усі 5 завдань виконані без допомоги.

### Крок C8. Аудит перед запуском

- **Мета:** перша версія безпечна і готова для реальних даних.
