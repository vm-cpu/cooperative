# Володі: перша ітерація реєстру гаражів

## Результат

Зручний український інтерфейс, який можна відкрити за постійним посиланням, перевірити на телефоні й обговорити дизайн. Перший крок — перегляд гаражів та власників на вигаданих даних. Редагування реальних даних і платежі — наступні ітерації.

**Тестувати тут:** https://cooperative-staging.vm-55d.workers.dev

**Production:** https://cooperative.vm-55d.workers.dev — не використовувати для експериментів.

Зараз за адресами є початкова сторінка; реєстр нижче — твоє завдання. Для входу використай свій доданий акаунт Cloudflare. Докладніше: [середовища](ENVIRONMENTS.md).

## Почни з цього

1. Відкрий staging, перевір вхід, світлу тему, читабельність на телефоні та вихід. Запиши незручності.
2. У Codex вибери репозиторій `vm-cpu/cooperative`. Прочитай `AGENTS.md`, `docs/PROJECT.md`, `docs/PLAN.md` і цей файл.
3. Онови `main`, створи гілку `feature/garage-registry`. Запусти `npm ci`, `npm run check`, `npm run dev`.
4. Знайди переданий приватний файл власників. Зафіксуй лише назви колонок і знеособлені проблеми структури. Якщо файла немає у твоєму середовищі — скажи, що його треба передати захищено, але продовжуй інтерфейс на тестових даних. Не завантажуй файл у Git або публічні сервіси, не копіюй ПІБ у чат/логи.
5. Попроси асистента пояснити план невеликими кроками. Після кожного кроку відкривай результат сам.

## Що реалізувати

### Чотири зрізи одних даних

- **Гаражі:** номер, ряд, власник або «Не вказано», тип боксу. Пошук за номером; фільтри за рядом, відсутнім власником, технічними боксами; сортування за рядом й номером; кількість знайденого.
- **Власники:** ім'я, кількість пов'язаних гаражів, їхні номери. Пошук за ім'ям, фільтр «Кілька гаражів». Одна людина може мати кілька боксів.
- **Ряди:** кількість боксів, з власником/без власника/технічних. Натискання відкриває відповідно відфільтрований список. Це групування, а не фізична карта.
- **Якість даних:** повтори ключа «ряд + номер», відсутні номери/ряди/власники, неоднозначні збіги власників. Не зливати людей автоматично тільки через однакове ім'я.

Картка гаража веде до власника; картка власника показує всі його гаражі. Повернення до списку зберігає пошук, фільтри та позицію. Є «Скинути фільтри», зрозумілий порожній результат і відновлення після помилки.

### Дані

Окремі сутності власника й гаража, стабільні ID та зв'язок між ними. Ключ гаража — ряд + номер; номер зберігається як текст, щоб не втратити літери, дроби чи початкові нулі. Оригінальні поля джерела зберігати незмінними, нормалізацію робити окремо. Співвласність, історію переоформлення й точні типи — записати як відкриті питання, не вигадувати.

Для прототипу підготувати явно позначені **вигадані дані**: власник з кількома гаражами, бокс без власника, технічний бокс, однакові імена різних людей, довге ім'я, неоднозначний номер, порожній результат. Якщо редагування показане як симуляція, прямо підписати це, дати скасування та відновлення тестового набору; не створювати фальшивої обіцянки збереження.

Зі слів замовниці: 574 бокси, 526 власників, 9 рядів (1–3, 5–10). Це орієнтири для майбутньої звірки з файлом, не числа для штучного підганяння. Фізичний план нададуть окремо: інтерфейс списків від нього не залежить.

### Дизайн, телефон і доступність

- Українська всюди; прості підписи й видимий початок роботи без пояснення автора.
- Шрифт від 18–20 px, елементи керування від 48×48 px. Контраст WCAG AA, статуси позначати текстом, не лише кольором.
- Перевірити ширини 320, 375, 768 px і настільний екран. На телефоні список/картки без горизонтального прокручування всієї сторінки; довгі імена не руйнують верстку.
- Для першої ітерації обов’язкова лише світла тема. Темна й системна теми не є критеріями приймання; їхню потребу перевіримо з користувачами пізніше. Наявний перемикач на стартовій сторінці можна залишити. Якщо додаткові теми доступні в реалізованому інтерфейсі, вони мають працювати послідовно на всіх його екранах, зберігати вибір і не скидати фільтри чи форми.
- Клавіатура: логічний Tab, видимий фокус, підписані поля, повернення фокусу після закриття діалогу. Збільшення 200%, перевірка екранним читачем і axe/Lighthouse.
- Завантаження, порожні дані, помилка і відсутність мережі мають чесне пояснення та наступну дію. Офлайн-збереження персональних даних у цій ітерації не додавати.

## Порядок здачі

1. Побудуй модель і вигаданий набір, тести зв'язків, пошуку, комбінованих фільтрів та сортування номерів.
2. Реалізуй списки й картки; додай зрізи рядів і якості даних.
3. Пройди сценарій: знайти гараж → відкрити власника → інший його гараж → повернутися без втрати фільтрів → оновити сторінку → вийти й увійти знову.
4. Запусти `npm run check`. Якщо додаєш API — серверна перевірка входу й ролей та тести 401/403 обов'язкові. Cloudflare Access сам по собі не реалізує ролі accountant/chair.
5. Створи один PR із заповненим шаблоном. Розгорни перевірений коміт **тільки на staging** за інструкцією ENVIRONMENTS. Якщо в Codex немає авторизації Cloudflare, підготуй PR і точний SHA для відповідального за розгортання; не передавай токени асистенту.
6. Перевір саме опублікований сайт на мобільному й настільному екранах у світлій темі. Якщо підтримуєш додаткові теми, перевір також їх. Додай скриншоти, результат accessibility-перевірки, SHA, staging-посилання, відомі обмеження та короткий сценарій тестування до PR.

## Критерії приймання

- Чотири зрізи показують узгоджені дані; переходи гараж ↔ власник працюють.
- Пошук/фільтри/скидання й порожній стан працюють; немає вигаданих реальних власників або автоматичного злиття тезок.
- Тестові дані очевидно позначені; жодних персональних даних у Git, логах чи відкритих ресурсах.
- Сценарій пройдено самостійно без автора на телефоні, у світлій темі, клавіатурою; критичні помилки доступності усунено.
- Перевірки зелені, PR готовий до перегляду; production не змінений.

Не входять у цю ітерацію: платежі, борги, розсилки, юридичне переоформлення, імпорт реальних даних, фізична карта, повноцінний PWA/offline. Не чекати цих рішень для роботи над прототипом.

## Наступний крок після отримання карти гаражів

Коли замовниця надасть карту/схему розміщення, добудувати інтерактивний план кооперативу на її основі. Це окремий наступний крок, який не блокує першу ітерацію списків.

1. Звірити ряди й номери на схемі з реєстром. Прив’язувати елементи плану до стабільних ID гаражів через перевірений ключ «ряд + номер». Пропуски й неоднозначні позначення показати як питання для уточнення; розташування не вигадувати.
2. Додати перегляд «План»: вибір гаража відкриває його картку; з картки можна перейти до гаража на плані. Пошук підсвічує знайдений гараж.
3. Забезпечити масштабування й переміщення на телефоні з видимими кнопками, доступ із клавіатури та рівноцінний доступ через список. Підписи й стани мають бути зрозумілі без розрізнення кольорів.
4. Перевірити відповідність наданій схемі, переходи план ↔ картка ↔ власник і мобільну зручність; викласти на staging в окремому PR. Обов’язкова тема залишається світлою.

До отримання схеми працювати зі списками та зрізами за рядами; не показувати умовне розміщення як справжній план кооперативу.
