# Робота з Git: гілки, коміти, pull request, відкат

Головна ідея: **кожна зміна — окремий шматок, який можна перевірити й відкотити окремо від інших.**
Якщо функцію зламано, ми прибираємо саме її, не зачіпаючи решти.

## 1. Гілки

**Одна функція або одне виправлення — одна гілка.** Не змішувати в одній гілці різні речі (наприклад, «пошук гаражів» і «оновлення бібліотек»).

| Що робимо                     | Назва гілки             | Приклад                    |
| ----------------------------- | ----------------------- | -------------------------- |
| Нова функція                  | `feature/<коротко-що>`  | `feature/garage-search`    |
| Виправлення помилки           | `fix/<коротко-що>`      | `fix/search-empty-state`   |
| Документація                  | `docs/<коротко-що>`     | `docs/git-workflow`        |
| Налаштування, інструменти     | `setup/<коротко-що>`    | `setup/staging-deploy`     |
| Зміна бази даних (міграція)   | `db/<коротко-що>`       | `db/add-owner-phone`       |
| Переробка без зміни поведінки | `refactor/<коротко-що>` | `refactor/registry-render` |

**Правила**

- Гілку створювати **завжди від свіжого `main`**:
  ```bash
  git switch main
  git pull
  git switch -c feature/garage-search
  ```
- **Гілка живе недовго: 1–3 дні.** Чим довше гілка живе, тим більше конфліктів з `main` і тим важче її перевірити.
- Якщо `main` пішов уперед — підтягнути зміни у свою гілку (merge, не rebase — так безпечніше для початківця):
  ```bash
  git fetch origin
  git merge origin/main
  ```
- Після злиття PR — **видалити гілку** (кнопка «Delete branch» у PR).
- **Ніколи** не комітити напряму в `main` і не робити `git push --force` у `main` чи в чужу гілку.

## 2. Розмір pull request

| Розмір PR (без `package-lock.json` і згенерованих файлів) | Оцінка                                     |
| --------------------------------------------------------- | ------------------------------------------ |
| до 200 рядків                                             | Ідеально: легко перевірити за 10–15 хвилин |
| 200–400 рядків                                            | Нормально                                  |
| понад 400 рядків                                          | Розбити на кілька PR                       |

**Один PR = один крок плану** (`docs/PLAN.md`). Наприклад, PR на 1600 рядків, який закриває 5 кроків одразу, — це 5 окремих PR.

### Як розбити велику функцію

Велику функцію робимо **послідовністю маленьких PR**, кожен з яких можна злити й відкотити окремо:

1. **Дані / модель** — структура даних і функції роботи з ними + unit-тести. Інтерфейсу ще немає.
2. **Перегляд** — екран, що показує дані (тільки читання).
3. **Пошук і фільтри** — окремо від перегляду.
4. **Редагування** — окремо, бо це зміна даних, ризикованіша.
5. **Шліфування** — тексти, доступність, дрібні покращення.

Якщо функція ще не готова для бухгалтера, але частину вже злито — **ховаємо її за прапорцем** (feature flag): наприклад, змінна середовища `FEATURE_EDITING=false` у production і `true` на staging. Так незавершений код є в `main`, але користувач його не бачить.

### Що завжди окремим PR

- **Оновлення залежностей** (Dependabot) — окремо від функцій.
- **Міграції бази даних** — окремо від коду, що їх використовує (див. розділ 5).
- **Масове форматування / перейменування** — окремо, інакше в ньому губляться реальні зміни.
- **Переробка (refactor)** — окремо від нової поведінки.

## 3. Коміти

**Один коміт = одна логічна зміна, після якої все працює** (тести проходять).

- Комітити часто: **кожні 30–60 хвилин роботи** або після кожного завершеного кроку.
- **Пушити хоча б раз за сесію** і завжди перед тим, як закінчується ліміт AI-асистента — щоб нічого не загубилося.
- Не змішувати в одному коміті: форматування + логіку, переробку + нову функцію.
- Повідомлення коміту — англійською, у наказовому способі, з типом на початку (Conventional Commits):

| Тип         | Коли                          | Приклад                                     |
| ----------- | ----------------------------- | ------------------------------------------- |
| `feat:`     | нова можливість               | `feat: add garage search by owner name`     |
| `fix:`      | виправлення помилки           | `fix: keep filters after returning to list` |
| `test:`     | тільки тести                  | `test: cover HTML escaping in owner names`  |
| `docs:`     | документація                  | `docs: describe rollback procedure`         |
| `refactor:` | переробка без зміни поведінки | `refactor: split registry render functions` |
| `chore:`    | інструменти, залежності       | `chore: bump wrangler to 4.161`             |
| `db:`       | міграції бази                 | `db: add phone column to members`           |

Перший рядок — до ~70 символів. Якщо потрібно пояснити **навіщо** — порожній рядок і пояснення нижче.

## 4. Злиття в `main`

- Тільки через PR, тільки з зеленими перевірками і після рев'ю.
- Спосіб злиття — **Squash and merge**: усі коміти гілки стають **одним комітом** у `main`. Тоді одна функція = один коміт, і відкотити її — одна дія.
- Назва squash-коміту = назва PR, тому назву PR пишемо так само, як коміт: `feat: ...`, `fix: ...`.

## 5. Відкат: як прибрати зламану зміну

### Код

1. **Швидко зупинити шкоду в production** (хвилина): відкотити Worker на попередню справну версію — див. «Відкат» у [ENVIRONMENTS.md](ENVIRONMENTS.md) (`wrangler rollback`). Це робить відповідальний за реліз.
2. **Прибрати зміну з коду**: на сторінці злитого PR натиснути **Revert** → GitHub створить новий PR, що скасовує саме цю зміну → перевірки → злиття → розгортання.
   Це працює чисто тільки тоді, коли PR був маленький і про одне — ще одна причина не робити великих PR.
3. Виправлення робимо **новою гілкою `fix/...`**, а не переписуванням історії.

### База даних (D1)

Відкат коду **не відкочує дані**. Тому міграції — найобережніша частина:

- Перед кожною міграцією на production — **резервна копія** (`wrangler d1 export`).
- Міграції **тільки додають** (нова таблиця, нова колонка з типовим значенням). Видалення й перейменування — у два кроки й двома окремими PR: спочатку код перестає використовувати старе поле, і лише потім (через кілька днів) окрема міграція його видаляє.
- Так новий код працює зі старою базою, а старий — з новою, і відкат коду нічого не ламає.
- Міграцію спочатку застосовуємо на staging, перевіряємо, і лише потім — на production.

## 6. Коротко: щоденний цикл

```bash
git switch main && git pull                 # 1. свіжий main
git switch -c feature/<що-роблю>            # 2. нова гілка
# ... робота маленькими кроками ...
npm run check                               # 3. перевірки
git add -A && git commit -m "feat: ..."     # 4. коміт
git push -u origin feature/<що-роблю>       # 5. пуш
# 6. відкрити PR, заповнити шаблон, дочекатися перевірок і рев'ю
# 7. Squash and merge → Delete branch
```
